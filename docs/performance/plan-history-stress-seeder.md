# Plan-history stress seeder

`plan_history_seed` adds stress projects to your **existing database and
workspace**, using the same `DATABASE_URL` as the API and normal seeder.
Use your usual frontend/API ports. No extra database or server is required.

Defaults: three projects named **History · 1000 revisions**, **History · 10000
revisions**, and **History · 50000 revisions**, each with **200 tasks, 3 tracks
and 6 sprints**, spread over **90 days**. Counts include creation operations.
This keeps board size constant while increasing history size. Revisions include
creation, titles, completion/reopening, task placement/order, sprint dates/track
changes and track titles/colors. Existing workspace members author the log.

From the repository root, with the same database environment as your API:

```bash
cargo run --release --manifest-path api/Cargo.toml --bin plan_history_seed
```

Reload your normal app, select the **Default** workspace, open **Plan**, choose
a **History** project and enable **Past**. Dates cover the preceding 90 days;
sprint dates stay around the current weeks.

Custom sizes use the same command and setup:

```bash
cargo run --release --manifest-path api/Cargo.toml --bin plan_history_seed -- \
  --revisions 10000,50000,100000 --tasks 500 --days 365
```

To target another existing workspace, append `--workspace UUID`. The default
is the normal fixture's Default workspace. The workspace must already exist;
the seeder creates no workspaces or users. It reads `.env` and `DATABASE_URL`
just like the normal API/seeder. The fallback URL is
`postgres://fira:fira@localhost:5432/fira`.

Reruns atomically replace only projects marked as generated by this seeder
in the selected workspace, along with their task/track/sprint rows and history.
Other projects, history, memberships and sessions are preserved. Profiles have
stable IDs scoped to the workspace. Reload the browser after reseeding;
the bulk generator emits no WebSocket nudges.

Every revision count must cover task/track/sprint creation. Profiles must be
unique. Limits: 1–10,000 tasks, 1–3,650 days, up to 1,000,000 revisions per
profile. Invalid arguments are rejected before database writes.

The generator validates payloads against the real `Op` type, bulk inserts
ordered log rows, and uses `project_at` to materialize matching live entities.
It does not measure production operation-handler throughput or concurrent
users. Historical API reads and browser interactions use the normal paths.

Validation:

```bash
cargo test --manifest-path api/Cargo.toml --test plan_stress_seed
```

Disposable-database tests check exact revision counts, chronological order,
range, authors, replay/live equality, early history, repeatability and
preservation of existing fixture projects/tasks/history when replacing profiles.
