# Sprint 36 — task-cli: write-only Notion

**Status:** planned
**Date:** 2026-11-12

## Goal

Let PMs follow engineering work in Notion without anyone copying it by hand.
`task-cli publish notion` pushes task content from the repository to Notion.
Nothing comes back: no import, no intake, no reading Notion content into the
repository. This replaces the two-way Notion design drafted for the old
sprint 35.

```text
repository documents -> task-cli publish notion -> Notion
```

## Prerequisite

[Sprint 35](35-task-cli-attachments.md): the `Attachments` section and file
hashes are reused for Notion.

## Ownership

The CLI writes one **"From repo" section** per task page and nothing else on
the body. Everything outside that section belongs to PMs.

| Notion page | Created by | CLI writes |
|---|---|---|
| Sprint ticket | PM | Nothing. The sprint file stores its link; the CLI uses it as the parent of the sprint's sub-tickets. |
| Task sub-ticket under a sprint ticket | CLI | Its "From repo" section, plus the properties: title, `Repo ID`, assignee, tags, estimate. |
| Standalone ticket (e.g. a bug a PM filed) | PM | Only its "From repo" section. No properties. |

Never written, on any page: **status** (PMs manage it in Notion), **order**
(see sprint 35's plan decision; PMs sort their own views), comments, page
content outside the section, and any property not listed above.

### The section

A single top-level toggle heading, `From repo`, created by the CLI's
integration. Its children are the CLI's content:

```text
▾ From repo
    ⓘ Generated by task-cli from the repository. Edits inside this section
      are overwritten; write notes outside it or in comments.
    <description>
    Attachments
      <file/image blocks, one per listed attachment>
    Subtasks
      ☐ Navigation
      ☑ Sidebar
    task-cli · <content hash>
```

- [ ] Found as the top-level toggle heading whose `created_by` is the
      integration's bot user (`GET /v1/users/me`) and whose text is
      `From repo`. No block IDs are stored in the repository.
- [ ] Created at the end of the page on first publish. PMs may collapse it
      or move it; verify that moving a block in the Notion UI keeps its ID.
- [ ] Deleted by a PM → recreated, shown as "create section" in the diff so
      the user can decline.
- [ ] The final line carries the content hash (see Diff). Missing or edited
      footer means "changed".

### Open questions (defaults chosen; confirm before starting)

- **Unlinked sprint file:** `publish notion` fails with "link the sprint
  ticket first" rather than creating a sprint ticket. *Default: fail.*
- **Standalone tasks without a link:** skipped with a notice (default), or
  created as CLI-owned standalone tickets.

## Linking and identity

- [ ] `task-cli link notion <file> [<task>] <url>` writes the link, shown in
      the diff like any change:
      - sprint: `notion: <page id>` in the frontmatter;
      - standalone task: `<!-- notion: id=<page id> -->` under the heading.
      Writing the line by hand is equally valid.
- [ ] Sub-tickets are found by their `Repo ID` property. Nothing about them
      is written into repository files.
- [ ] A linked PM page that is trashed or returns 404 (deleted, or access
      lost; the message says it cannot tell which) fails that file with a
      pointer to `link` again or remove the line.
- [ ] A sub-ticket that was trashed is recreated, shown as "create" in the
      diff so the user can decline.

## Notion setup

- [ ] `tasks/config.toml` gains `[notion] database_id = "…"`.
- [ ] `task-cli login notion` stores an internal integration token under
      sprint 34's credential rules; `TASK_CLI_NOTION_TOKEN` for CI. The
      database must be shared with the integration.
- [ ] Preflight before every diff: the database has `Repo ID` (text),
      sub-items enabled (`Parent item` relation), and the mapped properties
      with compatible types; the token can read and write. Fail with one
      message listing what is missing.
- [ ] Property mapping lives in config with defaults (`Assignee` people,
      `Tags` multi-select, `Estimate` number). Assignees match Notion users
      by email; no match leaves the property empty and adds a notice.
      Tags not yet in the multi-select are created by Notion on write; the
      diff says so.

## Diff without reading Notion content

Write-only means no Notion-blocks-to-Markdown converter.

- [ ] Sub-ticket properties are read back and compared field by field, using
      sprint 34's diff UI. The choice per field is only "publish" or "skip".
- [ ] Section: hash = SHA-256 of the canonical description, subtasks and
      attachment hashes, compared with the footer. The diff shows
      `section: unchanged`, `changed (will replace)` or `missing (will
      create)`. PM edits inside the section are not detected; the callout
      covers that.
- [ ] The publisher is its own module built on the canonical model. It
      compares local against a projection of Notion, and does not become a
      third side of `sync::build`/`plan`, which stay local ↔ Fira.

## Writing

- [ ] Markdown → blocks: headings, paragraphs, bullet/numbered lists,
      quotes, code, links, bold/italic/code spans; subtasks become `to_do`
      blocks with their checked state. Anything unsupported becomes a
      plain paragraph with the raw text. Headings inside the description
      are demoted to stay below the toggle heading.
- [ ] A changed section is replaced wholesale: archive the toggle's
      children, append the new ones in chunks of 100 (the API nests at most
      two levels per request, so deeper lists take follow-up appends), and
      write the footer last so an interrupted publish retries next time.
- [ ] Client-side pacing at about 3 requests/s; honour `Retry-After` on 429.
      Archiving is one request per block, so a long section takes seconds;
      show progress.
- [ ] No conditional writes exist in Notion. The residual race (someone
      edits inside the section between preview and write) is documented;
      it only loses edits the callout warns about.

## Attachments

Every listed attachment appears under the section's `Attachments` heading,
as Fira's panel shows them. Embeds in the description also render in place.

| Canonical | Notion |
|---|---|
| listed in `Attachments` | image block (image types) or file block under the section's `Attachments` heading |
| `![Layout](attachment:layout.png)` on its own line in the description | image block at that position as well |
| inline `see [spec](attachment:spec.pdf)` | text kept; the file is reachable from the `Attachments` list |

- [ ] Upload through Notion's file upload API and attach within its expiry
      window. Files are uploaded only when the section is replaced; their
      hashes are part of the section hash.
- [ ] Verify size limits and allowed types for the workspace's plan.
      Unsupported files show as "not publishable to Notion" and are
      skipped, never fatal.

## Membership changes

- [ ] A task moved to another sprint file: its sub-ticket's parent is
      updated to that sprint's ticket.
- [ ] A task removed from the repository: its sub-ticket is listed as "only
      in Notion" and left alone. No Notion deletes.

## CLI

```sh
task-cli login  notion
task-cli link   notion <file> [<task>] <url>
task-cli publish notion <sprint-or-task-file>
```

`task-cli diff` stays Fira-only. Update `help workflow` and `help agents`.

## Test scenario

Against a test Notion database with sub-items enabled.

1. **Preflight.** Remove `Repo ID` from the database, publish.
   → Fails before the diff, naming the missing property.
2. **Link.** Create a sprint ticket by hand; `link notion` the sprint file.
   → Diff shows the frontmatter line; accepted, it is written.
3. **Publish.** `publish notion tasks/sprints/<slug>.md`.
   → One sub-ticket per task under the sprint ticket with `Repo ID` and a
   "From repo" section: callout, description, every listed attachment,
   subtasks as to-dos, footer. The sprint ticket is unchanged. Republish →
   empty diff.
4. **Edit.** Change a title and a description; republish.
   → Title as a property diff, `section: changed (will replace)`; only that
   sub-ticket's section is rewritten.
5. **PM content.** Set status, reorder, and write a paragraph above the
   section on a sub-ticket; republish after another edit.
   → None of it is in the diff or touched.
6. **Standalone.** File a bug ticket in Notion with a PM-written body,
   `link` a single-task file to it, publish.
   → A "From repo" section appears at the end; the bug's properties and the
   PM's text are unchanged. Move the section to the top, edit the task,
   republish → updated in place, still at the top.
7. **Section deleted.** Delete the section on one page, republish.
   → `section: missing (will create)`.
8. **Move and remove.** Move a task to another linked sprint file; delete
   another from the repository; publish both files.
   → The moved sub-ticket changes parent; the deleted one is "only in
   Notion" and still there.
9. **Interrupted publish.** Kill the CLI mid-section-write, republish.
   → Section rewritten in full, footer last.

## Acceptance criteria

- [ ] Outside the "From repo" section, PM-created pages are never edited;
      only their links are stored.
- [ ] Sub-tickets and sections are found without writing Notion IDs for
      them into repository files.
- [ ] Republishing unchanged content is an empty diff and makes no writes.
- [ ] Status, order, comments and PM content outside the section are never
      written.
- [ ] Every listed attachment appears in the section; unsupported ones are
      skipped with a notice.
- [ ] Nothing is read from Notion into the repository, and nothing in Notion
      is deleted.

## Out of scope

Import and intake from Notion; Notion status mapping; detecting PM edits
inside the section; deleting Notion pages; a server-side Notion
integration; `diff` against Notion.
